## Day 1: Container basics and Container Apps (part 1)

**Goal:** package an app into an image, store it in a registry, and run it on Azure Container Apps.

### Concepts to know

- **Image vs container:** an image is the blueprint (read-only). A container is a running copy of it.
- **Dockerfile:** the recipe. Typical steps: pick a base image, copy code, install dependencies, expose a port, set the start command.
- **Azure Container Registry (ACR):** private storage for your images. Tags such as `myapp:v1` identify versions.
- **Why containers for AI apps:** same environment everywhere, easy scaling, easy rollbacks.
- **Azure hosting choices for containers:** Container Apps (serverless containers), AKS (full Kubernetes), App Service (web apps in containers), Container Instances (single, short-lived containers).

### The standard flow

```
Code -> Dockerfile -> Build image -> Push to ACR -> Deploy to host -> Test URL
```

### Commands to type at least once

```bash
# Create a registry
az acr create -n myregistry -g my-rg --sku Basic

# Build in the cloud and push (no local Docker needed)
az acr build -t myapp:v1 -r myregistry .

# List images
az acr repository list -n myregistry
```

### Container Apps core vocabulary

| Term | Meaning |
| --- | --- |
| Environment | A secure boundary (network and logging) that holds many container apps |
| Container app | Your running app inside an environment |
| Revision | An immutable snapshot of a version of your app. New settings create a new revision |
| Ingress | Lets traffic reach your app (external from the internet or internal only) |
| Replica | One running copy of a revision |

```bash
# Create an environment and deploy
az containerapp env create -n my-env -g my-rg -l eastus
az containerapp create -n my-app -g my-rg --environment my-env \
  --image myregistry.azurecr.io/myapp:v1 \
  --target-port 8080 --ingress external
```

### Hands-on lab

Build a tiny web API (any language), push it to ACR with `az acr build`, deploy it to Container Apps with external ingress, and open the URL.

### Self-check questions

1. What is the difference between an image and a container?
2. Why use `az acr build` instead of building locally?
3. What is a revision, and when is a new one created?
4. What is the difference between external and internal ingress?

**Memory trick:** *"Build, Push, Deploy."* Every container story is these three words.

## Day 2: Container Apps (part 2) and AKS

**Goal:** scale and update apps safely, then understand when Kubernetes is the better choice.

### Container Apps: the topics that matter

- **Scaling:** driven by rules. HTTP concurrency, CPU or memory, or event sources (queue length, for example) through **KEDA**. Container Apps can scale to zero replicas to save cost.
- **Revisions and traffic splitting:** run two revisions and split traffic (for example 90% to v1, 10% to v2) to test safely. This is blue-green or canary style deployment.
- **Revision modes:** *single* (one active revision) or *multiple* (several active at once, needed for traffic splitting).
- **Secrets and environment variables:** store secrets at the app level and reference them from environment variables.
- **Managed identity:** lets the app authenticate to Azure services without passwords.
- **Dapr:** an optional sidecar that provides building blocks such as service-to-service calls, state and pub/sub.
- **Jobs:** run-to-completion work (batch, scheduled tasks) instead of always-on apps.

```bash
# Scale between 0 and 5 replicas
az containerapp update -n my-app -g my-rg --min-replicas 0 --max-replicas 5

# Enable multiple revisions
az containerapp revision set-mode -n my-app -g my-rg --mode multiple

# Split traffic between revisions
az containerapp ingress traffic set -n my-app -g my-rg \
  --revision-weight my-app--v1=90 my-app--v2=10
```

### AKS: the topics that matter

AKS is Azure's managed Kubernetes. Azure runs the control plane for you. You manage the worker nodes and your workloads.

| Kubernetes object | Plain-English meaning |
| --- | --- |
| Pod | Smallest unit. One or more containers running together |
| Deployment | Keeps N copies of a pod running and handles rolling updates |
| Service | Stable network address in front of changing pods (ClusterIP, LoadBalancer) |
| Ingress | HTTP routing rules (host and path) into services |
| ConfigMap and Secret | Configuration and sensitive values for pods |
| Namespace | A logical folder to separate teams or apps |
| Node pool | A group of VMs of the same size (for example a GPU pool for AI inference) |

```bash
# Create a cluster and connect
az aks create -g my-rg -n my-aks --node-count 2 --attach-acr myregistry --generate-ssh-keys
az aks get-credentials -g my-rg -n my-aks

# Deploy and inspect
kubectl apply -f deployment.yaml
kubectl get pods
kubectl describe pod <pod-name>
kubectl logs <pod-name>
kubectl scale deployment myapp --replicas=5
```

**Scaling in AKS:** *Horizontal Pod Autoscaler* adds or removes pods. *Cluster autoscaler* adds or removes nodes.

### Decision flow: Container Apps or AKS?

```
Need Kubernetes APIs, custom operators, or deep network control?
      YES -> AKS
      NO  -> Need simple serverless scale-to-zero with low ops?
                YES -> Container Apps
```

### Troubleshooting cheat sheet (AKS)

| Symptom | Likely cause | First command |
| --- | --- | --- |
| ImagePullBackOff | Wrong image name, or AKS cannot pull from ACR | `kubectl describe pod` |
| CrashLoopBackOff | App crashes on start (bad config or missing secret) | `kubectl logs <pod>` |
| Pending | Not enough node resources | `kubectl describe pod` |
| Service unreachable | Selector labels do not match pods | `kubectl get endpoints` |

### Self-check questions

1. How do you test a new version with only 10% of traffic in Container Apps?
2. What is KEDA used for?
3. What is the difference between a Pod, a Deployment and a Service?
4. Which autoscaler adds nodes, and which adds pods?
5. Give two reasons to choose AKS over Container Apps.

**Memory trick:** *"ACA = easy mode, AKS = pro mode."*

## Day 3: Azure Cosmos DB for NoSQL (AI focus)

**Goal:** model data, understand cost and partitioning, and run vector search for RAG.

### Core concepts

- **Hierarchy:** account, then database, then container, then items (JSON documents).
- **Partition key:** decides how data is spread across physical partitions. Pick a value with many distinct values and even access (for example `userId`, not `country`). A bad key creates "hot partitions".
- **Request Units (RU/s):** the currency of throughput. Every read or write costs RUs. Point reads (id plus partition key) are the cheapest. Cross-partition queries cost more.
- **Throughput modes:** provisioned, autoscale, serverless.
- **Consistency levels (strong to weak):** Strong, Bounded staleness, Session (default), Consistent prefix, Eventual.
- **Global distribution:** replicate to many regions for low latency and high availability.
- **Change feed:** an ordered stream of changes in a container. Useful to trigger downstream work (for example re-embedding updated documents).

### Vector search in Cosmos DB

Store embeddings in the same document as your data, then search by similarity.

Three things must be set up:

1. **Vector embedding policy:** which path holds the vector, its data type, dimensions and the distance function.
2. **Vector index in the indexing policy:** the index type used for fast search.
3. **Query with `VectorDistance`.**

| Index type | Meaning | Use when |
| --- | --- | --- |
| flat | Exact, brute force | Small data, up to a few thousand vectors |
| quantizedFlat | Compressed vectors, brute force | Medium data, faster and cheaper |
| diskANN | Approximate nearest neighbour | Large data, low latency at scale |

**Distance functions:** cosine, dotproduct, euclidean. Use the function your embedding model recommends (cosine is the common default).

```sql
SELECT TOP 5 c.title, VectorDistance(c.embedding, @queryVector) AS score
FROM c
ORDER BY VectorDistance(c.embedding, @queryVector)
```

Important: the vector index and policy must be set when the container is created. Plan for it up front.

### The RAG flow with Cosmos DB

```
User question -> Embedding model -> query vector
   -> Cosmos DB VectorDistance -> top matching documents
   -> add them to the prompt -> LLM -> grounded answer
```

### Security

Prefer **Microsoft Entra ID with role-based access** (managed identity) over account keys.

### Hands-on lab

Create a container with a vector policy, insert a few documents with embeddings, and run a `VectorDistance` query.

### Self-check questions

1. What makes a good partition key?
2. What is an RU, and which operation is cheapest?
3. Name the three vector index types and when to use each.
4. Which consistency level is the default?
5. Where in the RAG flow does Cosmos DB sit?

**Memory trick:** *"Policy, Index, Query."* The three pieces of Cosmos vector search.

## Day 4: PostgreSQL and Azure Managed Redis

**Goal:** add vectors to a relational database, then use Redis to make AI apps faster and cheaper.

### Part A: Azure Database for PostgreSQL

Use it when your data is relational (joins, transactions, SQL) and you also want similarity search.

**Key extensions:**

- `vector` (pgvector): adds a vector column type and similarity operators.
- `azure_ai`: calls Azure AI services (for example generating embeddings) directly from SQL.
- Extensions must be allow-listed in the server parameter `azure.extensions` before `CREATE EXTENSION` works.

```sql
CREATE EXTENSION vector;

CREATE TABLE docs (
  id serial PRIMARY KEY,
  content text,
  embedding vector(1536)
);

-- Similarity search: smallest distance first
SELECT id, content
FROM docs
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 5;
```

| Operator | Distance |
| --- | --- |
| `<->` | Euclidean (L2) |
| `<=>` | Cosine |
| `<#>` | Negative inner product |

**Vector indexes:**

| Index | Idea | Trade-off |
| --- | --- | --- |
| IVFFlat | Groups vectors into lists | Faster build, lower recall. Build after loading data |
| HNSW | Layered graph | Better recall and speed, uses more memory and build time |
| DiskANN | Disk-based graph (Azure extension) | Large datasets with lower memory use |

**Rule:** the number of dimensions in the column must match your embedding model output.

**Hybrid search:** combine vector similarity with normal SQL filters (for example `WHERE tenant_id = 5`) or full-text search for better results.

### Part B: Azure Managed Redis

Redis is an in-memory store: extremely fast, ideal for things that are read often and can expire.

| AI use case | How Redis helps |
| --- | --- |
| Response cache | Same question, same answer, no LLM call |
| Semantic cache | Similar questions reuse an answer, found by vector similarity |
| Session and chat memory | Keep conversation history per user, with expiry |
| Rate limiting | Count requests per user |
| Vector search | Search embeddings in memory (through the search capability) |

**Key ideas:**

- **TTL (time to live):** automatic expiry so the cache does not go stale.
- **Cache-aside pattern:** check cache first, on a miss read the source, then store the result.
- **Eviction policy:** what Redis removes when memory is full.
- **Authentication:** prefer Microsoft Entra ID over access keys.

```
Question -> Embed -> Similar entry in cache?
      YES -> return cached answer (fast, cheap)
      NO  -> call LLM -> store answer with TTL -> return
```

### Decision table: which store?

| Need | Choose |
| --- | --- |
| Global scale JSON documents plus vectors | Cosmos DB |
| Relational tables plus vectors | PostgreSQL |
| Speed, caching, sessions | Redis |

These are not either/or. A common design is PostgreSQL or Cosmos DB as the source of truth with Redis in front as a cache.

### Self-check questions

1. Which pgvector operator means cosine distance?
2. Why must you allow-list an extension before creating it?
3. HNSW or IVFFlat: which gives better recall?
4. What is a semantic cache and why does it save money?
5. What does TTL protect you from?

**Memory trick:** *"Cosmos = Cloud-scale docs, Postgres = Proper tables, Redis = Rapid."*

## Day 5: Backend services, secrets and configuration

**Goal:** connect services reliably and never leak a secret.

### Part A: Integrating backend services

| Service | Use it for | Key words |
| --- | --- | --- |
| Service Bus | Reliable messaging between apps (long AI jobs, ordered work) | Queue (one receiver), Topic and subscription (many receivers), dead-letter queue, peek-lock |
| Event Grid | Reacting to events (blob uploaded, resource changed) | Push, event subscription, routing |
| Event Hubs | High-volume streaming (telemetry, logs) | Partitions, consumer groups |
| Azure Functions | Small event-driven code | Triggers and bindings |
| API Management | A managed front door for your APIs | Policies, rate limit, JWT validation, keys |

**Message handling basics:**

- **Peek-lock:** a message is locked while processing. Complete it on success, abandon it on failure.
- **Dead-letter queue:** where messages go after too many failed attempts. Always monitor it.
- **Idempotency:** your handler should be safe if the same message arrives twice.
- **Queue-based load leveling:** a queue absorbs traffic spikes so slow AI work is not overwhelmed.

```
Upload document -> Event Grid -> Function -> Service Bus queue
   -> Worker (embed and store in DB) -> Done
```

**API Management for AI:** put one gateway in front of model endpoints to apply authentication, throttling, logging and routing in one place.

### Part B: Secrets and configuration

**Golden rule:** no passwords or keys in code, config files or images.

| Service | Stores | Notes |
| --- | --- | --- |
| Key Vault | Secrets, keys, certificates | Access through RBAC. Supports soft delete and purge protection |
| App Configuration | Settings and feature flags | Labels for environments (dev, prod). Can hold Key Vault references |
| Managed identity | An identity for your app | System-assigned (tied to the resource) or user-assigned (reusable) |

```
App --(managed identity)--> Entra ID gives a token
    --> Key Vault returns the secret (if the role allows it)
```

**Typical role names:** *Key Vault Secrets User* (read secrets), *App Configuration Data Reader* (read settings). Always give the least privilege needed.

**Code habit:** use the Azure SDK's `DefaultAzureCredential`. It uses your developer login locally and the managed identity in Azure, so the same code works in both places.

```python
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

client = SecretClient(vault_url="https://myvault.vault.azure.net",
                      credential=DefaultAzureCredential())
value = client.get_secret("db-password").value
```

**Feature flags:** turn features on or off without redeploying (for example roll out a new model to 10% of users).

### Self-check questions

1. Queue or topic: which one delivers a message to many subscribers?
2. What happens to a message that keeps failing in Service Bus?
3. Event Grid or Event Hubs: which is for high-volume streaming?
4. System-assigned or user-assigned identity: which can be shared by several resources?
5. Why use `DefaultAzureCredential`?
6. What is the benefit of a feature flag?

**Memory trick:** *"Identity first, keys last."*

## Day 6: Observability and full review

**Goal:** find and fix problems fast, then revise everything once.

### The three pillars

| Pillar | Question it answers | Azure tool |
| --- | --- | --- |
| Logs | What happened? | Log Analytics (queried with KQL) |
| Metrics | How is it performing? | Azure Monitor metrics (CPU, requests, latency) |
| Traces | Where did this request spend time? | Application Insights (distributed tracing) |

**Key ideas:**

- **Azure Monitor:** the umbrella service for collecting, analysing and alerting.
- **Log Analytics workspace:** the central store that you query with KQL.
- **Application Insights:** application performance monitoring. Use the OpenTelemetry-based Azure Monitor distro to send telemetry from your code.
- **Alerts and action groups:** rules that notify people or trigger automation.
- **Container Apps:** console and system logs flow to Log Analytics, and you can stream them live.
- **AKS:** Container Insights collects node and pod data. Use `kubectl logs` and `kubectl describe` for quick checks.

### KQL you should be able to read

```kusto
// Failed requests in the last hour, grouped by result code
requests
| where timestamp > ago(1h)
| where success == false
| summarize count() by resultCode
| order by count_ desc

// Slowest operations
requests
| summarize avg(duration) by name
| top 5 by avg_duration desc
```

KQL pattern: *table | filter | summarize | sort*. Think of a pipeline.

### Troubleshooting flow

```
User says "it is slow or broken"
   |
   1. Check alerts and metrics: is it everywhere or one service?
   2. Open the trace: which dependency is slow (DB, LLM, cache)?
   3. Query logs: errors and exceptions around that time
   4. Fix, redeploy, confirm in metrics
```

**AI-specific signals to monitor:** token usage, model latency, throttling (429 errors), cache hit rate, queue length, dead-letter count.

### Exam-day tips

- Read the last line of the question first. It tells you what is being asked (cheapest, most secure, least effort).
- Look for keywords: "serverless" suggests Container Apps, "no credentials" suggests managed identity, "similar meaning" suggests vector search.
- Eliminate two options first, then compare the remaining two.
- When two answers both work, pick the one with less management effort and better security.
- Flag hard questions and return to them. Do not lose time.
- For code questions, check the SDK or CLI names, parameters and the order of steps.
